Memex V2 · search quality audit

What survived the search audit

A beginner-friendly record of how Memex search works, what we changed, and what the local search evaluations measured. The selected branch now keeps a faster text-matching path, gives uncommon query words more weight, prefers one passage that supports the query, and records the limits of the eval.

How search works

Search starts with the words a person types. The application may first rewrite those words into a clearer search plan. It then makes an embedding, which is a list of numbers that captures the query's meaning. The database combines that meaning search with ordinary word matching. Finally, the application orders the results and loads the saved content. Our evaluation repeats a set of searches with known answers, then checks whether those answers appear near the top and how long each search takes.

Queryuser words
Planrewrite or keep
Find possible matchesmatch words and meaning
Order resultsstrongest matches first
Show resultsfirst page, then more
Words used below. A chunk is a small stored passage from a saved item. A distractor is a result that looks related but is the wrong answer. A pairwise judgment asks whether the right item appears above one specific wrong item. A page is one slice of results, such as results 11 to 20; pagination is choosing that slice. The saved library is the eval's corpus. A holdout set is a separate set of queries that we did not use while tuning; this audit has none.

The eval is a measurement outside the product flow. It repeats the same 156 queries, then checks quality and time so a ranking change does not hide a speed regression.

The SQL problem appeared in the exact-anchor and phrase branches. An anchor is a strong word or phrase that should appear in the saved text. Before the change, the database cleaned the same chunk text again for each anchor term and again for each phrase. The cleanup was correct, but the repeated work became expensive on a corpus with thousands of chunks.

How the candidate SQL changed

Before

Each branch scanned scoped chunks and evaluated memex_normalize_search_text(csc.text) inside every term or phrase match. 

for each exact term or phrase:
  scan scoped chunks
  normalize(chunk.text)
  apply the same regex

Retained

A materialized CTE computes the padded normalized text once. The old regex rules, scope joins, and candidate sets stay the same. 

normalized_scoped_chunks AS MATERIALIZED (...)
  WHERE EXISTS(valid exact term OR non-empty phrase)

anchor candidates and phrase candidates
  read normalized_text

Speed work in plain English

A search result is produced in stages. Each stage answers a different question: what did the person mean, which saved items could match, which passages support the match, and which results should appear first?

Meaning search

The embedding lets a query about “ways to keep a private code project fresh” find text that uses different words. This is useful for meaning, but it can also return a broad result that only sounds related.

Word and passage search

Exact words, phrases, and the passage that contains them provide stronger evidence. Coverage ranking asks how much of the query a result supports, then combines that evidence with the database rank.

Toy example: clean text once

There are two related cleanup steps in this report. The early exact-word and phrase path lowercases text, replaces punctuation with spaces, collapses repeated spaces, and trims the result. A later coverage-only step also removes accent marks so its text terms match the TypeScript ranker. Keeping these steps separate avoids claiming that the early speed fix changed accent handling. 

early exact/phrase cleanup:
"Hello, WORLD!"  →  "hello world"

later coverage-only cleanup:
"Trần Hùng — café"  →  " tran hung cafe "

lasts for one database request; it is not a cross-query cache.

What the speed measurements actually show

Early speed path. The old path repeatedly cleaned the same saved text. In the no-rewrite comparison, average database retrieval fell from about 1.43 s to 0.52 s. The slow-tail p95 fell from 7.53 s to 3.42 s, while the middle case moved only from 135 ms to 122 ms. Some slow examples changed from 20.2 s to 4.8 s, 16.0 s to 4.9 s, and 15.7 s to 5.1 s. Most already-fast searches changed little. The same 156 query requests were compared, so this is useful local evidence, not a randomized benchmark.
Exact early measurements

Retrieval mean was 1,427.224 ms → 521.667 ms (63.45% lower, or 2.74× faster); p50 was 135 ms → 122 ms; p95 was 7,531 ms → 3,419 ms (54.6% lower). Wall-clock mean was 2,355.135 ms → 1,402.923 ms (40.43% lower). The query objects were identical in all 156 cases. Hit@1 rose from 110 to 114 and Hit@10 stayed at 136. The selected examples were Claude Code grep 20,199 → 4,763 ms, Anthropic tools 16,018 → 4,902 ms, and AI only services 15,704 → 5,134 ms.

The first attempt needed a correction. Reusing cleaned text initially cut average retrieval from 1.38 s to 0.72 s and p95 from 7.38 s to 3.81 s, but made the middle case slower: 136 ms to 415 ms. We fixed this by skipping the cleanup when a search had no words or phrases for that part of the database to check. Separately, rewritten search compared with its cached reference moved average retrieval from 3.75 s to 1.04 s and p50 from 2.81 s to 562 ms. Rewrite-cache and provider timing also differed, so that whole wall-clock change cannot be credited to SQL alone. The later 542 ms skip reference is a separate rerun; it does not replace the earlier 522 ms measurement.

Copyable plain-English summary

Search was repeatedly cleaning the same saved text while checking different
words and phrases. We changed it to clean each passage once per search and
reuse the result, and to skip that work when it was not needed.

In our local evaluation, average retrieval time fell from about 1.43 seconds
to 0.52 seconds; one slow query fell from about 20 seconds to 5 seconds.
The main benefit was fewer long waits: already-fast searches changed little.

Retained changes

1. Clean the text once, and only when needed

The database checks the same words and phrases as before. It now prepares each passage once and shares that prepared text between those checks. If none of these checks are needed, it does not prepare the text at all.

Implementation and focused measurements

The migration is supabase/migrations/20260905100000_reuse_scoped_normalized_search_text.sql. It replaces repeated normalisation with one scoped materialized CTE. The EXISTS guard checks for a valid exact term or a non-empty phrase before the CTE can scan chunks. This matters because downstream references can otherwise force the CTE to run even when ordinary searches have no exact candidate input. The implementation is committed in 4064e1817 and retained by the selected branch.

Semantic check: anchor candidates were 1,193 before and after; phrase candidates were 156 before and after. Both directions of set difference were zero. A single-anchor check and a phrase-only check also had zero differences. No ranking rule or scope rule was changed.

In a rollback-only local profile of the complete RPC, the empty-input branch fell from 404.2 ms without the guard to 74.3 ms with it, about 82% less time in this isolated check. Anchor candidates were 1,193 before and after; phrase candidates were 156 before and after, with zero IDs in either direction of set difference. The first normalized version reduced mean retrieval time but made many fast searches slower; the guard targets that exact regression.

2. Compare words across the whole item and one passage

The ranker now receives text from exact matched chunks. For each result it computes document-wide term coverage and matched-evidence coverage, keeps title terms, then averages the two values. This gives a result credit when the whole document supports the query while also rewarding the chunk that actually matched. 

coverage = (documentCoverage + matchedEvidenceCoverage) / 2
adjustedRank = reciprocalRank * (1 + weight * coverage²)

The focused tests cover a document-supported result, a matched-evidence result, and empty evidence with title support. This was a useful comparison: it preserves broad document support and local passage evidence. The selected branch later tested IDF weighting and the strongest single chunk. The 50/50 implementation is committed in 26875348a.

3. Keep the selected IDF best-any coverage rank

IDF means that a less common query word contributes more than a very common word. Best-any means that a result uses the strongest single canonical chunk it has, instead of adding weak matches scattered across many unrelated chunks. The kept normalized-fast variant reached 123/156 Hit@1, 149/156 Hit@10, MRR 0.847, and nDCG 0.862. It exposed 16/22 known negatives and got 25/33 evaluated pairwise judgments correct, or 25/34 on the fixed label denominator. Its first skip run measured 750 / 443 / 3,544 ms retrieval mean / p50 / p95. The repeat measured 762.397 / 438 / 3,724 ms and returned identical complete results. The selected ranking is committed and pushed at cad8445ed, 34c2f8e69, and HEAD 7bc7ca53b.

4. Make eval reports explain their own limits

The harness now records a dataset SHA-256, requested and effective user IDs, execution mode, concurrency, and timeout. It also reports judgment coverage separately from quality: known negatives, pairwise judgments, chunk judgments, graded relevance, and multiple-target cases. This prevents a high score from hiding a thin judgment set. The provenance change is retained in the branch history. The final denominator and label updates are committed in 34c2f8e69 and 7bc7ca53b.

Data incident and limits of the conclusion

Incident. A nested npm invocation dropped a filter. It ran 99 tests, with 63 failures, and a cleanup removed 620 global chunks: 8,066 became 7,446. This was outside the intended scoped evaluation operation.

The final saved library has 298 items, all 159 distinct expected content IDs, and 3,873 scoped indexed chunks; the global index has 7,446 chunks. The latest local migration is 20260905110000. A full 156-case replay was identical. That is useful evidence for the eval scope, but it does not prove that unrelated user data was preserved. There is no exact deleted-ID list or recovery artifact, and no reindex was run during this phase. This report therefore records the incident instead of claiming full library integrity.

Next validation

The remaining product decision is the SQL ranking contract before the SQL limit. The current search retrieves a bounded candidate set and then applies TypeScript coverage ranking, title boosts, annotation ordering, and parent/child suppression. Moving only a partial score into SQL would not be coherent. If this work continues, define one complete pre-pagination ranking contract and measure its recall, latency, and pagination stability.

  1. Keep the same 156 cases, user, migration state, and query inputs.
  2. Compare the current order with one rank-before-limit variant.
  3. Measure Hit@1, Hit@10, MRR, known-negative exposure, retrieval p50/p95, wall p50/p95, and exact top-10 stability.
  4. Stop if the result is a clear regression or if the quality gain is too small for the latency cost.

The selected branch keeps the SQL guard and IDF best-any normalized-fast rank. The repeat skip run returned identical complete results and similar timing. A broader or held-out corpus can test whether the quality result generalises. Any further SQL pagination change must preserve the richer ranking contract without introducing duplicate or skipped pages.
